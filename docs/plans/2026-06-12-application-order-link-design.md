# 신청 → 결제 연결 설계 (2026-06-12)

## 목표

신청서(`applications`)와 주문(`orders`)을 연결해 "신청 후 결제" 플로우를 만든다.
운영자가 결제한 참가자를 신청서와 매칭할 수 있어야 한다.

## 확정된 제품 결정

1. **신청 필수**: 신청서 없이는 결제할 수 없다. 모든 신규 주문은 신청서에 연결된다.
2. **자동 승인**: 결제(paid/demo_paid)가 완료되면 연결된 신청서가 접수/검토중 상태일 때 자동으로 승인된다. 거절/취소된 신청은 되살리지 않는다.
3. **데모 동일 적용**: 화면 확인용 demo_paid 주문도 동일하게 신청서 연결과 자동 승인을 따른다.

## 연결 방식: 신청 확인 토큰

방문자는 익명이므로 결제 시 "내 신청"임을 증명할 수단이 필요하다.
신청 생성 시 서버가 64자 난수 토큰을 발급하고, 브라우저가 localStorage에 보관했다가
결제 시 제출한다. 기존 `checkout_token`과 같은 관용구다.
(application_id 직접 사용은 ID가 비밀이 아니라서 배제, 신청+주문 단일 RPC는 "신청 필수"와 모순이라 배제)

## 스키마

- `applications.confirmation_token text` — 발급 토큰, unique 부분 인덱스(where not null). 기존 행 null 유지.
- `orders.application_id uuid references applications(id) on delete set null` + 인덱스. 기존 주문 null 유지(소급 연결 안 함).

## 서버 로직 (RPC 교체)

- `create_public_application`: 토큰 생성·저장, 응답에 포함.
- `create_public_order`: `p_application_token` 파라미터 추가.
  - 토큰으로 신청서 조회, 같은 모임인지·거절/취소 상태가 아닌지 검증, `application_id` 연결.
  - 같은 신청서에 paid/demo_paid 주문이 이미 있으면 차단 (`APPLICATION_ALREADY_PAID`, 409) — 1인 다좌석 방지.
  - 같은 신청서의 유효한 pending 주문은 자동 취소 후 새 주문 생성 — 결제창 닫고 재시도할 때 pending이 쌓여 좌석을 이중 점유하던 실버그 해결.
  - demo_order는 생성 즉시 demo_paid이므로 이 시점에 자동 승인.
- `confirm_toss_payment_order`: 주문 paid 전환 후 같은 트랜잭션에서 연결 신청서를
  접수/검토중 → 승인으로 변경.

## 프론트엔드

- `public-storage.js`: 모임별 `{meetup_id → token}` 맵 헬퍼 (기존 문자열 셋 헬퍼와 동일한 크기 제한).
- 드로어: 토큰이 없으면 결제 버튼이 "신청 후 결제" 잠금 상태. 누르면 신청 폼 포커스 + 안내.
  신청 성공 시 토큰 저장 후 즉시 해제.
- 체크아웃: 토스/데모 페이로드에 `applicationToken` 포함.
  `APPLICATION_NOT_FOUND` 응답이면 저장 토큰 폐기 후 재신청 안내.
- localStorage 유실 시 복구는 재신청(새 토큰 발급). 중복 신청서는 수용한다.
- 관리자: 주문 목록에 신청자 이름(FK 임베딩), 신청 목록에 결제 여부 표시.

## 단계적 롤아웃 (기존 lock 마이그레이션 패턴)

1. 1차 마이그레이션 — 토큰 발급 추가, `p_application_token`은 *선택*(있으면 연결): 구버전 프론트 무중단.
2. 엣지 함수 배포 (토큰 전달).
3. 프론트엔드 배포 (토큰 수집·제출 + UX 게이트).
4. 실플로우 확인 후 2차 잠금 마이그레이션 — 토큰 *필수* 전환.
- CI 브라우저 스모크를 "신청 제출 → 결제 모달" 순서로 수정해야 4단계 이후에도 통과한다.

## 테스트

- 토큰 맵 저장·체크아웃 페이로드 단위 테스트
- RPC 검증 규칙(모임 일치, 상태, 중복 결제 차단, 자동 승인) 마이그레이션 소스 계약 테스트
- 결제 버튼 잠금/해제 상태 헬퍼 테스트
- 엣지 함수 토큰 전달 소스 계약 테스트

## 범위 제외

- 기존 데이터 소급 연결 (불가능, null 유지)
- 신청 단계 좌석 점유 (현행 유지 — 좌석은 주문만 점유)
- 무료 모임 결제 플로우 (현재 제품에 없음)
